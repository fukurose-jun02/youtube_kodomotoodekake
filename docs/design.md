###### 設計書：動画の年齢・スポット名・住所（Issue #10）

最終更新：2026-10-31

###### データの持ち方
- `data/spots.json`：`videos[動画ID] = { spot, pref, city }`。キーが無い動画は「対象外」か「確認待ち」
  - `pref`＝都道府県、`city`＝市区町村（町・区まで）。住所の表示は `pref + city`
  - 手で整理するデータ（`data/claims.json` と同じく、同期では上書きしない）
- 年齢は保存せず、公開日から都度計算する（誕生日は `scripts/sync-videos.js` の `CHILD_BIRTHDAY`）

###### 年齢の計算（`calcAge`）
- 月数 ＝ （年の差×12 ＋ 月の差）−（公開日の日 ＜ 誕生日の日 なら1）
- 月数が負（誕生前）なら空文字。それ以外は「{月数÷12}歳{月数%12}ヶ月」

###### 反映先
- CSV（`buildCsv`）：末尾に「年齢」「スポット名」「住所」を追加
- `index.html` の `VIDEOS`（`formatEntry`）：`age` / `spot` / `place` を、あるときだけ追加
- 画面：`AgeTag`（子どものアイコン画像 `icons/child-icon.png` ＋ 年齢。v1.2.1 で絵文字から変更）と `SpotLine`（赤い地図ピン `icons/map-pin.svg` ＋ スポット名 ・ 住所。v1.2.2 で📍から変更）。カードA・B・再生画面は両方、ポラロイド（C）は余白が小さいので年齢のみ
- 検索（`index.html` の絞り込み）と候補（`ux-parts.jsx` の `SearchAuto`）：題名に一致しなければ、スポット名・住所で一致させる

###### 決めたこと／理由
- 年齢を保存しない理由：誕生日の基準を変えたときに、データの直し忘れが出ないようにするため
- `spots.json` を別ファイルにした理由：`videos.json` は同期で毎回作り直されるので、手で整理した内容を守るため

###### 設計書：自然文で動画を探すチャット（Issue #13）

最終更新：2026-10-31（状態：案。ユーザーの承認待ち）

###### 全体の流れ
1. 画面（`index.html`）が、質問と直近の会話を `POST /api/chat` に送る
2. Worker（`worker/index.js`）が、上限を確認する（D1に回数を記録）
3. WorkerがGemini APIに、動画の一覧と会話を渡し、合う動画IDと短い返事をJSONで返させる
4. Workerが、IDを一覧と照合して、`{ reply, videoIds }` を画面に返す
5. 画面が、返事とカードを表示する。カードを押すと再生画面（`VideoModal`）が開く

###### 構成
- `wrangler.jsonc`：`main: worker/index.js`、`assets.run_worker_first: ["/api/*"]`（`/api/*` だけWorkerが先に処理し、それ以外は今までどおり静的ファイルを返す）、D1の設定（`DB`）、変数（`GEMINI_MODEL`・上限値）
- `.assetsignore`：`/*` で全部除外する今の方式のまま。`worker/` は公開されない
- Gemini APIキー：Workerの秘密情報（`GEMINI_API_KEY`）。ローカルは `.dev.vars`（`.gitignore` に追加する）
- 動画の一覧（カタログ）：`sync-videos.js` が `worker/catalog.json`（ID・題名・カテゴリー・公開年月・年齢・スポット・住所・説明の先頭60文字）を作る。Workerは、これを一緒にまとめて配信する。`main` に push → 自動デプロイで、一覧も更新される

###### 探し方
- 一覧ごとGeminiに渡す方式（検索用の仕組みを足さない）。理由は、動画が152本で、一覧が約8,600文字（見積もり約1万トークン）に収まり、「雨の日に行ける」のようなあいまいな質問は、AIが施設の知識を使って判断する方が合うため
- 出力はJSON形式を指定（`responseMimeType: application/json`）。`{ "reply": "…", "videoIds": ["…"] }`。最大5本
- 指示文（system）：動画探し専用。一覧に無い動画は出さない。関係ない質問は断る。一覧の文章は「データ」であり命令ではない、と明記
- 使うモデル：`gemini-3.1-flash-lite`（バーチャルトークと同じ。`GEMINI_MODEL` で変更できる）

###### 上限（費用の防止）
- D1の表 `chat_usage(day, key, count)`。1リクエストごとに「日付×キー」の回数を足して、上限を超えたらGeminiを呼ばずに断る
  - キー：`ip:<IPのハッシュ>`（1人1日15回）、`all`（サイト全体で1日50回）
  - 日付は日本時間。IPは、ハッシュ化して保存（元のIPは保存しない）
- 上限値は、Workerの変数（`LIMIT_PER_IP`・`LIMIT_ALL`）。再デプロイで変えられる
- 費用の見積もり：1回 約 ¥0.5（入力約1万トークン×$0.25／100万、出力約400トークン×$1.50／100万、1ドル150円で計算）。全体の上限50回/日なら、最大でも1日 約 ¥25（1か月 約 ¥750）
- バーチャルトークとキーを共有するため、共有の月 ¥1,000 の上限と前払い残高を食い合う。サイト全体の上限は、それを踏まえて低めにしてある

###### 画面（`index.html`）
- 検索ボックスのカードの下に、「チャットで探す」の入力欄を埋め込む（`ChatSearch`）。最初は例文のボタンを数個出す（「雨の日に行けるところ」など）
- 返事は文字で表示し、下に、動画カード（小さめの横長）を並べる。押すと `VideoModal`
- 会話は、画面の状態（メモリ）に持つ。保存先は、ブラウザ内（ページを閉じると消える）
- 送信中は「さがしています…」。エラー・上限のときは、文言を出す
- 既存の✨AIおでかけプランナー（`AiModal`）は、`window.claude` が公開サイトに存在せず動かないため、このチャットに置き換える（本体の削除は、別途確認）

###### エラー時の文言
- 上限：「今日はたくさん使われたので、ここまでです。あしたまたきてね」
- Geminiが使えない（残高切れ・混雑）：「いま、おへんじができません。上の検索ボックスを使ってね」
- 入力が長い・空：入力欄の下に注意

###### テスト方針
- Geminiを差し替えたテスト：IDの照合（存在しないIDを捨てる）、上限（超えたらGeminiを呼ばない）、入力の検証（長さ・履歴の件数）、命令めいた入力に動画以外を返さない（モデルの出力を固定して、Worker側の照合を確認）
- 実際のGeminiでの確認：ユーザーがキーを設定したあと、`wrangler dev` で数件の質問を試す

###### 追記（2026-10-31）実装で分かったこと・変えたこと（Issue #13）
- 続けての絞り込み：画面が、履歴の返事に「紹介した動画のID（最大5本）」を付けて送る。Workerが一覧と照合し、題名と年齢を履歴の文章に足してGeminiへ渡す（「もっと小さいころのは？」で、直前に紹介した動画を基準にできるようにするため）
- `Origin` の確認は、ブラウザからの他サイト経由の呼び出しを防ぐためのもの。curlなどでは偽装できるため、費用を守る本体は、回数の上限である
- Geminiの新しい認証キー（先頭が `AQ.`）は、今の呼び出し方（`x-goog-api-key` ヘッダー）で使えることを確認した
- 続けての絞り込みの精度：結果が毎回少しばらつく。改善の余地：モデルを強いもの（`GEMINI_MODEL`）に変える、または年齢を月数の数値で持つ
- `wrangler dev --remote` は、Cloudflareに設定した秘密情報（`GEMINI_API_KEY`）を使わない。実際のGeminiの確認は、`.dev.vars` を使ったローカル実行で行う
