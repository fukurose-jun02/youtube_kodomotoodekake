###### 2026-08-13 Google Driveの「.gsheet」「.gsite」「.gscript」ファイルの正体

Google Driveをローカルのフォルダとして同期すると、実際のスプレッドシートやサイトの中身ではなく、Googleのサーバー上にある本体への「ポインタ（住所のメモ）」のような小さなファイルが置かれる。中身はJSONで、`doc_id`（そのファイルを一意に指し示すID）だけが書かれている。だから見た目のファイルサイズはとても小さい。実際の内容を読むには、Google Drive側のAPIを通じて`doc_id`を使ってアクセスする必要がある。

###### 2026-08-13 なぜ「マスターデータ」と「表示用のサイト」は分けて考えるべきか

今回のように「スプレッドシートに手入力→コピペでサイトに反映」という運用は、データの元（マスター）と表示（サイト）が同じ手作業でつながっている状態。ここを自動化する時のポイントは、「どこが正のデータか」を1箇所に決め、そこから他を自動生成する一方通行の流れを作ること。逆流（サイト側を直接手で編集してマスターとズレる）が起きると、どちらが正しいか分からなくなってしまう。

###### 2026-08-13 なぜSupabaseのような外部DBを使わなかったか

このサイトはGitHub Pagesで公開している「静的サイト」＝サーバーを持たず、あらかじめ作られたHTMLファイルをそのまま配信する仕組み。動画データも「サイトを作る時（ビルド時）」に1回だけ使えれば十分で、訪問者がサイトを見るたびにデータベースへ問い合わせる必要がない。そのため、Supabaseのような「常時稼働してリアルタイムに問い合わせるためのデータベース」を導入しても機能を活かせず、外部サービスへの依存・APIキー管理の手間が増えるだけになる。今回はリポジトリの中にJSONファイルを1つ置く、というシンプルな形を選んだ。

###### 2026-08-13 カテゴリーをYouTubeの「タグ」欄に持たせた理由

YouTubeの動画には、視聴者に見える「タイトル」「概要欄（説明文）」の他に、視聴者には見えない「タグ」というキーワード欄がある（検索用のメタデータ）。今回、動画のカテゴリー（おでかけ／保育園 等）をこの「タグ」欄に入れておくことにした。概要欄に直接書く方法もあったが、それだと視聴者が読む説明文の中に事務的な分類情報が混ざってしまう。タグ欄は元々そういう「裏方のメタデータ」を書くための場所なので、用途に合っている。

###### 2026-08-13 プログラムが自動で書き換える範囲を「マーカーコメント」で区切る理由

`index.html`のようなファイルに「ここから自動生成、ここまで」という目印（マーカーコメント）を置いておくと、自動化スクリプトは目印の間だけを機械的に置き換えればよくなる。目印がないと、スクリプトは「配列の始まりと終わりはこの辺りだろう」と推測するしかなく、周りの手書きコードを誤って壊してしまうリスクがある。目印を置くのは「ここは触っていい場所」だと明示する、簡単だが効果の大きい工夫。

###### 2026-08-13 APIキーは「発行したら終わり」ではなく「制限をかける」までがセット

Google CloudなどでAPIキーを発行すると、最初は制限なし＝そのキーが持つ権限をすべて使える状態で作られる。もし漏洩すると、意図しないサービスまで勝手に使われてしまう危険がある（今回、過去にGemini用のキーがコード内に平文で残っていて発覚したのが実例）。発行したら必ず「このAPIだけに使う」という制限をかけることで、万一漏れても被害の範囲を絞れる。

###### 2026-08-13 「.env」と「.gitignore」の役割

`.env`はパスワードやAPIキーなど、外部に漏らしてはいけない情報を書いておく専用のファイル。`.gitignore`に`.env`と書いておくことで、Gitが「このファイルは絶対にリポジトリに含めない」と覚えてくれる。これにより、コードは全部GitHubに公開しつつ、秘密の情報だけは自分のパソコンの中に留めておく、という使い分けができる。

###### 2026-08-13 「APIキー」と「OAuth認証」の違い

APIキーは「このアプリ（プログラム）自身が誰であるか」を証明するだけの鍵で、いわば店の入館証のようなもの。一方OAuth認証は「特定のユーザー本人が、自分のデータへのアクセスをこのアプリに許可する」という、人単位の許可を得る仕組み。YouTubeでいうと、APIキーだけでは「誰でも見られる公開情報」しか取得できないが、OAuthでチャンネル所有者本人としてログイン・許可すれば、限定公開や非公開など「本人しか見えないはずの情報」にもアクセスできるようになる。今回、動画が全部「限定公開」設定だったためAPIキーだけでは0件しか取れず、OAuthへの切り替えが必要になった。

###### 2026-08-13 OAuthの「ループバックリダイレクト」とは

昔はターミナル上のCLIアプリでOAuth認証する際、Googleの認証ページに表示された「コード」をコピーしてターミナルに貼り付ける方式（Out-of-Band方式）が使えたが、セキュリティ上の理由でGoogleは2023年にこれを廃止した。代わりに使われるのが「ループバックリダイレクト」という方式：プログラムが自分のパソコンの中に一時的な小さなWebサーバー（`http://127.0.0.1:ランダムなポート番号`）を立てておき、ブラウザでの認証が終わったらGoogle側がそのアドレスに「認証コード」を送り返してくる。人間の目には「ブラウザで許可ボタンを押しただけ」に見えるが、裏側ではこの一時サーバーが自動でコードを受け取り、トークンに交換している。

###### 2026-08-13 OAuthの「テストユーザー」とアプリの「公開ステータス」

Google Cloud ConsoleでOAuthアプリを作ると、最初は「テスト」ステータスになっており、この状態では事前に登録した「テストユーザー」のGoogleアカウントしかログインできない（それ以外は「アクセスをブロック」エラーになる）。これは、正式審査（Google検証）を受けていない未完成のアプリを誰でも使えてしまわないための安全装置。個人利用の小さなツールであれば、正式審査を受けずに「アプリを公開」ボタンで本番ステータスに切り替えることもでき、その場合はテストユーザー登録が不要になる代わりに、ログイン時に「このアプリは確認されていません」という警告が出る（自分が作った安全なアプリだと分かっていれば、警告を無視して進めてよい）。

###### 2026-08-13 「クライアントシークレット」が後から見られなくなった理由

OAuthクライアントを作った際に発行される「クライアントシークレット」は、以前は管理画面でいつでも再表示できたが、Googleは仕様を変更し、現在は作成した瞬間の1回しか表示されない（後からは末尾数文字のマスク表示のみ）。これはパスワードマネージャーなどと同じ考え方で、「一度発行した秘密情報は、盗み見られるリスクを減らすため、正規のフローでしか再利用できないようにする」というセキュリティ強化の一環。見逃してしまった場合は、同じクライアントに新しいシークレットを追加発行できる（古いシークレットを無効化することも可能）。

###### 2026-08-13 YouTube APIで「動画」と「ショート」が区別できない理由

YouTubeの管理画面（Studio）では「動画」と「ショート」ではっきりタブが分かれているが、YouTube Data API（プログラムからデータを取得する公式の窓口）には、この2つを直接区別するためのフラグ（項目）が用意されていない。API上はどちらも同じ「アップロードされた動画」として扱われる。そのため、判定したい場合は、動画の長さで推測したり、YouTubeの「ショート専用ページ（`/shorts/動画ID`）」にアクセスした時の挙動（本当にショートならそのページのまま、通常動画ならリダイレクトされる）を利用したりといった、公式には保証されていない「間接的な推測」に頼る必要がある。今回はこの後者の方法を使い、実際のショート数（275本）に近い精度（277本）で判定できた。

###### 2026-08-13 「結果整合性（けっかせいごうせい）」とは何か

YouTubeのようなGoogleの大規模なサービスは、1つのデータを世界中の複数のサーバー（コピー）に分散して保存している。データを書き換えた直後は、まだ全部のコピーへの反映が終わっておらず、「どのサーバーに読みに行くか」によって新しい値と古い値のどちらが返ってくるか分からない瞬間がある。これを「結果整合性（Eventual Consistency）」と呼び、少し待てば全部のコピーが揃って正しい値に落ち着く。今回、タグを書き込んだ直後に読み込むと1件だけ古い状態（未分類）が返ってきたが、これはバグではなくこの仕組みによる一時的なブレで、再実行したら解消した。

###### 2026-08-13 同じAPIキーでも「権限（スコープ）」を機能ごとに分ける理由

OAuth認証では、1つのアプリ（クライアントID・シークレット）に対して複数の「権限の許可書（リフレッシュトークン）」を使い分けることができる。今回、動画データを読むだけの`sync-videos.js`は「読み取り専用」の許可書、動画のタグを書き換える`apply-categories.js`は「書き込み可」の許可書、と別々に発行した。もし1つの許可書に全部の権限をまとめてしまうと、読み取りしかしないはずのスクリプトが誤動作やバグで書き込みをしてしまうリスクや、その許可書が漏れた時の被害範囲が広がるリスクがある。用途ごとに権限を必要最小限に分けておくのは、セキュリティの基本的な考え方（最小権限の原則）。

###### 2026-10-15 OAuth同意画面の「テスト」と「本番」の違い
GoogleのAPIを使うアプリは、OAuth同意画面に「テスト」か「本番（In production）」の状態を持つ。「テスト」の間は、登録したテストユーザーしか使えず、発行された認証トークン（リフレッシュトークン）が7日で失効する。このため、同期スクリプトが週1回程度しか動かないと毎回「トークンが無効」になり、ブラウザでの再認証が必要になる。「本番」に切り替えると、この7日失効はなくなる。ただしGoogleの審査を受けていない（未検証）アプリだと、認証時に「このアプリは確認されていません」という警告が出る。自分だけが使う個人用ツールなら、警告の「詳細」から続行すれば使える。本番に切り替えた後は、一度だけ再認証してトークンを取り直す必要がある。

###### 2026-10-18 Cloudflare の Pages と Workers の違い、Durable Objects
Cloudflare には静的サイトを公開する方法が2つある。Cloudflare Pages は昔からある「ファイルを置くだけ」の仕組みで、Workers の静的アセット配信は、より新しい仕組み。見た目はどちらも同じように公開できるが、後から機能を足すときに差が出る。Pages は Durable Objects（後述）が部分対応で回避策が要り、定期実行（Cronトリガー）も使えない。Workers なら同じプロジェクトにそのまま足せる。チャットのように「接続している全員に同じ内容をリアルタイムで届ける」機能は、Durable Objects と WebSocket の組み合わせで作る。Durable Object は「同じ名前なら必ず同じ1つの場所で動く小さなプログラム」で、チャットルームのような「みんなが集まる場所」の役目を担う。将来の機能追加を考えて、今回は Workers 側を選んだ。独自ドメインを使う場合、Workers はネームサーバーが Cloudflare 管理である必要がある（Pages はなくても可）。

###### 2026-10-18 許可リスト方式（.assetsignore）による公開事故の防止
サイトを公開するとき、フォルダの中身を丸ごと配信すると、APIキーが入った `.env` ファイルなども一緒に公開されてしまうおそれがある。そこで `.assetsignore` というファイルに「まず全部を除外し、公開したいものだけ再許可する」と書く。これを許可リスト方式という。逆に「公開したくないものを列挙する」方式は、新しいファイルを足したときに書き忘れて公開してしまう事故が起きやすい。今回は `index.html`・`tweaks-panel.jsx`・`uploads/` だけを許可し、公開後に `.env` や `scripts/` が404になること（見えないこと）を実際に確認した。

###### 2026-10-24 許可リスト方式は「新しいファイルを足したら許可も足す」必要がある
`.assetsignore` は「全部除外して、公開するものだけ再許可する」許可リスト方式にしてある。事故（`.env` の公開など）を防げる反面、デザイン更新で `backdrops.jsx` と `ux-parts.jsx` という新しいファイルを足したのに許可リストへ書き足さないと、リポジトリには入っていても公開サイトには出ず404になる。画面は `index.html` がこれらを読み込もうとして失敗し、壊れる。新しいファイルをサイトに足すときは「コミットする」と「公開の許可リストに足す」をセットで行う。公開URLで各ファイルが200で返るかを確認するのが確実。
